The Challenge

In a finance app, a timeout does not mean failure. A request can reach the server and be saved while the response gets lost on the way back. If the user then taps "Save" again, the expense is recorded twice and every summary becomes wrong.

The second problem: once the connection is back, the app has to know for certain whether that operation went through, without guessing.

Technical Solution

  • Operation ID: every write carries a unique ID from the client. Retrying with the same ID and payload returns the original result with no new effect.
  • Receipt: the outcome of every operation is stored as applied, rejected, or not_applied. No "pending" state is ever treated as success.
  • Reconciliation: a client that lost a response can ask for the result, or ask the server to close that operation as not_applied.
create_expense_v1 (excerpt, PL/pgSQL)

Writes and the resolver take the same transactional advisory lock on (user_id, operation_id). As a result, a late request cannot commit after its operation has already been declared not applied.

-- Serialize per (user_id, operation_id); released automatically on commit/rollback
perform pg_advisory_xact_lock(app_private.operation_lock_key(v_user_id, v_operation_id));

select r.* into v_existing
  from app_private.operation_receipts r
 where r.user_id = v_user_id and r.operation_id = v_operation_id;

if found then
  if v_existing.outcome = 'not_applied' then
    return mutation_receipt_json(v_existing);  -- already closed by the resolver
  end if;
  if v_existing.payload_fingerprint is distinct from v_fingerprint then
    raise exception 'IDEMPOTENCY_PAYLOAD_MISMATCH';  -- same ID, different payload
  end if;
  return mutation_receipt_json(v_existing);    -- identical retry: no new effect
end if;

Data Access

  • The client has no direct access to the transactions table. Every read and write goes through RPC functions.
  • RPC functions run as SECURITY DEFINER with a locked search_path and only touch data owned by the signed-in user.
  • Amounts are stored as whole rupiah, not decimals, so there are no rounding errors.

Verification

  • 8 pgTAP test files (about 3,800 lines) covering schema, permissions, idempotency, and reconciliation.
  • Tests on the mobile side and in a shared contracts package for input validation.
  • GitHub Actions CI runs typecheck, lint, tests, and a secret scan on every push.

How This Project Is Built

I write the scope, design decisions, and the spec for every task first, as a PRD and 22 decision records, before any code exists. The implementation is written with the help of an AI coding agent, one task at a time, and a task is only accepted after it passes every CI check and the database tests.

This is deliberate: in a finance domain, questions like "what does a timeout mean" have to be decided and written down, not left to a guess while coding.
